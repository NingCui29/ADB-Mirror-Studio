# 版本管理与问题修复计划

ADB Mirror Studio 从重新整理后的 `V1.0.0` 开始使用三段式版本号 `主版本.次版本.修订版本`，Git 标签和对外显示统一使用大写 `V` 前缀，例如 `V1.0.1`。后续版本号只递增，不重复使用，也不覆盖已经正式发布的版本。

## 版本升级规则

| 变更级别 | 升级方式 | 示例 | 适用范围 |
|---|---|---|---|
| 小问题 | 修订版本 `PATCH` 加 1 | `1.0.0 → 1.0.1` | 局部缺陷、显示微调、提示修正、兼容性补丁和不改变既有用法的稳定性修复 |
| 大问题 | 次版本 `MINOR` 加 1，修订版本归零 | `1.0.0 → 1.1.0` | 跨模块严重缺陷、较大流程调整、明显性能改造，以及保持向后兼容的新功能 |
| 大版本 | 主版本 `MAJOR` 加 1，其余归零 | `1.0.0 → 2.0.0` | 不兼容升级、核心架构或主要界面重做、设置或数据格式无法无感兼容、系统要求发生重大变化 |

安全漏洞、数据丢失、无法退出、安装或卸载损坏、录屏或镜像导致系统无法正常操作等问题，无论代码改动大小，均按最高处置优先级处理。版本号仍根据对用户的兼容性影响决定；能够兼容修复时可发布紧急补丁版本。

## 判定原则

### 发布修订版本

满足以下条件时发布 `PATCH`：

- 修复范围局部，现有功能入口和操作流程不变。
- 不要求用户重新配置，不改变设置文件和公开数据格式。
- 不引入需要单独学习的新功能。
- 安装版可以直接覆盖升级，便携版可以保留用户数据后替换。

典型版本：`V1.0.1`、`V1.0.2`。

### 发布次版本

满足以下任一条件时发布 `MINOR`：

- 问题影响多个模块，需要较大范围重构或交互调整。
- 增加用户可感知的新功能，但仍兼容现有设置和使用方式。
- 进行显著的性能、设备兼容性或可靠性改造。
- 需要设置迁移，但可以自动完成且能够安全回退。

典型版本：`V1.1.0`、`V1.2.0`。后续小修复继续递增为 `V1.1.1`、`V1.1.2`。

### 发布主版本

满足以下任一条件时发布 `MAJOR`：

- 旧设置、工作流或发行格式无法保持兼容。
- 核心架构、主要导航或关键交互整体重做。
- 最低 Windows、Android 或硬件要求发生重大变化。
- 移除或替换已有能力，用户必须执行迁移操作。

主版本发布前必须提供迁移说明、回退方法和已知问题。典型版本：`V2.0.0`。

具体版本由已确认问题的影响范围决定，不为了凑版本号加入未验证功能。

## 问题处理流程

1. **登记**：记录复现步骤、期望结果、实际结果、Windows/Android 版本、连接方式和相关日志。
2. **定级**：标记阻断、严重、一般或轻微，并判断属于 `PATCH`、`MINOR` 还是 `MAJOR`。
3. **复现**：在修改前稳定复现；无法复现时先补充诊断信息，不直接猜测修复。
4. **修复**：从独立分支提交最小必要改动，同时加入回归测试或明确的人工测试步骤。
5. **验证**：运行 Release 单元测试，并覆盖安装、升级、卸载、启动、退出和受影响功能。
6. **发布**：更新版本元数据、说明文档、安装版与便携版，计算 SHA256 后创建新的 GitHub Release。
7. **观察**：发布后检查下载、安装和更新检测；发现回归时停止扩展范围，优先发布后续补丁。

## 发布门槛

每个正式版本必须满足：

- 工作区无未提交修改，目标提交已经同步到远端默认分支。
- `commercial/Directory.Build.props` 中的产品、程序集和文件版本一致。
- 所有自动化测试通过，新增修复具有对应回归验证。
- 安装版完成全新安装、覆盖升级和卸载测试。
- 便携版完成解压启动、正常退出和核心功能冒烟测试。
- README、版本说明、文件名、下载链接和应用内显示使用同一版本号。
- GitHub Release 同时提供安装版和便携版，并公布与本地一致的 SHA256。
- 正式标签使用 `V主版本.次版本.修订版本`；发布后不移动、不覆盖。

## 分支与提交约定

- 小问题：`fix/问题摘要`
- 大问题或兼容功能：`feature/问题或功能摘要`
- 大版本准备：`release/v2.0.0`
- 修复提交：`fix: 修复内容`
- 功能提交：`feat: 功能内容`
- 发行提交：`release: V1.0.0`

一个发行版本可以包含多个已验证修复，但紧急问题不等待普通计划，应单独发布补丁版本。
